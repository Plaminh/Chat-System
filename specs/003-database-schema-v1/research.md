# Research: Database Schema Version 1

## Decision 1: Canonical relationship keys

**Decision**: Store friendships and direct-conversation pairs in canonical low-ID/high-ID order, while blocks and friend requests remain directed.

**Rationale**: Canonical ordering makes reversed duplicates enforceable with ordinary `CHECK` and `UNIQUE` constraints and avoids triggers.

**Alternatives considered**: Bidirectional duplicate rows were rejected because they can drift; expression-only uniqueness was rejected because canonical columns are easier to query and document.

## Decision 2: Conversation specialization

**Decision**: Use `conversations` for shared metadata, `direct_conversations` for the unique direct pair, and `conversation_members` for participation in both direct and group conversations.

**Rationale**: The split keeps exactly one direct pair per direct conversation while membership carries role, join/leave, and personal history-clearing state used by both conversation types.

**Alternatives considered**: Separate direct/group message tables duplicate message behavior; storing participant arrays weakens referential integrity.

## Decision 3: Message lifecycle semantics

**Decision**: Model global recall on `messages` using `unsent_at` and `unsent_by`; model per-user hiding in `message_deletions`; model conversation clearing using `conversation_members.history_cleared_at`.

**Rationale**: These three UI actions have different visibility and retention effects and must remain queryable independently.

**Alternatives considered**: A single deletion flag cannot express per-user visibility; physically deleting rows destroys moderation/history evidence.

## Decision 4: Moderation independence

**Decision**: Keep spam-report workflow status independent from `users.account_status` and allow an optional referenced message.

**Rationale**: A report may be dismissed, reviewed, or resolved without necessarily changing the reported account; account sanctions remain separate actions.

**Alternatives considered**: Status values such as `account_locked` were rejected because they conflate case handling with account state.

## Decision 5: Activity as source events

**Decision**: Store individual `app_open`, `direct_chat`, and `group_chat` events with user, optional conversation, and event time.

**Rationale**: Source events support time-bounded counts and `COUNT(DISTINCT ...)` analytics without persisting calculated counters in `users`.

**Alternatives considered**: Precomputed counters cannot answer arbitrary date ranges and can diverge from source activity.

## Decision 6: PostgreSQL constraint strategy

**Decision**: Use `BIGINT GENERATED BY DEFAULT AS IDENTITY`, `TIMESTAMPTZ`, explicit foreign keys, `CHECK` constraints, normalized lowercase states, and targeted B-tree indexes. Use case-insensitive unique expression indexes for username/email while preserving display text.

**Rationale**: These are native PostgreSQL capabilities compatible with Spring JDBC and require no ORM, trigger, or extension.

**Alternatives considered**: UUIDs conflict with the numeric-ID requirement; `CITEXT` adds an extension dependency; triggers add hidden behavior unnecessary for V1.

## Decision 7: Cross-table rules deferred to backend transactions

**Decision**: Document, rather than emulate with triggers, rules such as conversation-kind specialization, membership authorization, group owner/admin guarantees, report prior-interaction eligibility, and unsend permissions.

**Rationale**: These rules span tables or current-user authorization and belong in the Version 2 backend transaction boundary.

**Alternatives considered**: Database triggers and stored procedures were rejected as unnecessary V1 complexity and would duplicate future service authorization.

## Decision 8: Runtime validation safety

**Decision**: Provide static validation on every environment and transactional SQL assertions for an explicitly isolated test database. Never point destructive fixtures at an unknown database.

**Rationale**: The repository may not have PostgreSQL installed or configured, and the workflow prohibits risking existing data.

**Alternatives considered**: Auto-creating and dropping a guessed local database was rejected as unsafe; syntax-only confidence without executable fixtures was rejected as insufficient documentation.

## Decision 9: Minimal encrypted-group storage

**Decision**: Support client-side E2EE with one active versioned X25519 public key per user, client-generated AES-256-GCM group-key epochs, and one RFC 9180 HPKE base-mode envelope per recipient public key and epoch. Group mode is immutable after creation; User Clients generate fresh random nonces; verified public-key replacement requires complete rotation in every affected encrypted group before sending resumes. Store only public keys, opaque envelopes, message ciphertext, nonce, tag, and epoch references.

**Rationale**: The model gives authorized User Clients the only private keys needed to open group-key envelopes. The server can authorize, persist, and forward records without possessing a plaintext private/group key or independent decryption key. The per-user recipient model is the smallest coherent choice for the existing single-user-session client requirements.

**Alternatives considered**: The previous shared server-wrapped-key design was rejected because the server could decrypt. A flag-only design, plaintext/server-recoverable keys, searchable plaintext copies, and custom envelope protocols were rejected. Per-device key distribution was deferred because V1 has no device identity/session model and must not claim unsupported multi-device behavior.

## Decision 10: Historical activity retention

**Decision**: Conversation deletion sets `user_activity_logs.conversation_id` to null while retaining `activity_type`, user, and timestamp.

**Rationale**: Registration/activity statistics remain reproducible after conversation cleanup, and the event type still classifies direct versus group activity.

**Alternatives considered**: Cascading activity deletion loses historical statistics; aggregate tables are unnecessary for the expected scale.
